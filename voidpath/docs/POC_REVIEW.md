# POC review findings (carried into Wave S)
Collected by the five-lens review of the proof of concept before the full-game rebuild. Most were not yet independently verified: treat each as a strong lead, check it in the code, and fix it if it still applies after your Wave S changes. Each item names the files involved; the Wave S owner of those files owns the fix.

## R1. [critical] A second New Journey cannot open the supply crates, so the Bridge Keycard can't be obtained and the run can't be finished

- Files: /home/user/Research/voidpath/src/world/explore.js, /home/user/Research/voidpath/src/world/world.js, /home/user/Research/voidpath/src/world/props.js, /home/user/Research/voidpath/src/core/game.js
- Failure: The player opens any crates in journey 1 (in practice always the keycard crate, which every path to the boss needs). They then die (Game Over -> Return to title) or beat the game (Complete -> Return to title) and pick New Journey. The world reset re-locks the bridge door and brings the SENTINEL back, but every crate opened earlier looks sealed and can never be opened again. With no keycard the door stays locked and the game can't be completed without reloading the page. The Medi-Gel, Ether and Revive crates are also lost.
- Evidence: explore.js:434-435 opens a crate with `c.setOpen(true); it.enabled = false;`. That disables the crate's interactable, which props.js:338 creates. When resetGame() (game.js:55) clears the flags, world.js:563 `syncFlags` only calls `c.setOpen(false, true)`. setOpen (props.js:322-328) recolours the LED and resets the lid but never re-enables the interactable, and _pickTarget (explore.js:327) skips `!it.enabled`. Headless proof (shots/review/A3, ?q=low at 960x540): journey 1 opened eng_2 and logged `{"flags":{"crate_eng_2":true},"inv":{...,"keycard":1}}`. The run then lost a battle, used the game-over row 'Return to title' and started New Journey. Journey 2 logged flags `{}` with no keycard. Standing next to the crate gave `prompt:null` and `eng_2:enabled=false,opened=false`. Enter did nothing (inventory unchanged), and the bridge door prompt stayed 'Inspect' (locked). The screenshot A3/A2-journey2-keycard-crate.png shows the sealed crate with its red LED and no prompt.
- Suggested fix: Keep the interactable in step with the crate's state. Give the crate a reference to its interactable and set `it.enabled = !open` inside setOpen, or have World.syncFlags re-enable crate interactables whose flag is cleared. Then explore.js no longer needs to touch `it.enabled` directly.

## R2. [major] Title soft-lock: pressing New Journey while the 'Return to title' fade is still running hides the title and nothing starts

- Files: /home/user/Research/voidpath/src/ui/title.js, /home/user/Research/voidpath/src/core/game.js, /home/user/Research/voidpath/src/core/titleScene.js
- Failure: On the Game Over or Complete screen the player picks 'Return to title' and keeps mashing Enter (or the gamepad's A button, or double-taps on touch) through the fade. The first hidden press moves the title from 'Press Start' to the menu, and the second activates New Journey, which is ignored because the fade is still running. The player is left on a title backdrop with no menu and no response to input, and only a page reload recovers. If they came from Game Over the input context is 'battle', so not even the pause menu opens.
- Evidence: game.js:69-79 toTitle() runs a 1.4 s fade and calls `this.change('title')` at the midpoint (line 76). TitleState.enter then shows the title overlay at once (titleScene.js:372 -> showUI 375-377), with no input lock, while the fade-in (about 0.7 s) is still running. Nothing ever shows the title again. Headless proof (shots/review/B, and the earlier run in shots/review/s2): call toTitle(), then press Enter twice as the title appears. Five seconds later the log reads `{"state":"title","t":true,"title":null}`. After the transition ended and more Enter/Esc/Space presses: `{"state":"title","t":false,"title":null}`. B-title-after.png shows the backdrop with no UI at all. Tab then opened the pause menu over the title (B-title-tab.png).
- Suggested fix: Don't let the title act before the transition has finished. Either show the title UI from the toTitle promise's `.then` (change('title', { deferUI: true }) at the midpoint, then showUI() after the fade), or have Title._activate check engine.transitioning before calling hide(). Also make newJourney return a boolean so the title only hides when the journey has really started.

## R7. [major] Default 'high' preset renders about 3.7 MP on HiDPI laptops, with 12 direct lights per pixel and 5 full-resolution half-float post passes, and never falls back on its own

- Files: voidpath/src/core/engine.js, voidpath/src/main.js, voidpath/src/world/lighting.js, voidpath/src/core/postfx.js
- Failure: Player on a typical HiDPI laptop: a MacBook at default scaling, or a Windows ultrabook with a 2560x1600 panel at 150% (renders 2560x1410). Every lit floor, wall and sprite pixel runs MeshStandard GGX for 9 point + 1 spot + 2 directional lights plus a PCF-soft shadow lookup. Then about 5 full-screen RGBA16F passes run, each 30 MB per target, roughly 400 MB of render-target traffic per frame including the 26 tilt taps. On Intel UHD/Iris-class integrated GPUs this exceeds the 16.7 ms budget, so the field and battles run at a sustained, visibly juddery 20-35 fps (estimate from the code; SwiftShader cannot measure GPU time). Nothing steps quality down.
- Evidence: engine.js:16-20: high = { pixelRatioCap: 2.0, shadows: true, bloomScale: 1.0, tiltTaps: 13 }. engine.js:22 MAX_PHYSICAL_HEIGHT = 1440 caps only the height, and engine.js:208 sets pixelRatio = min(dpr, cap, 1440/h). main.js:33 returns isTouchDevice() ? 'medium' : 'high', so every desktop and laptop starts on high. lighting.js:13 POOL.high = 8, plus the hero PointLight (63) and the SpotLight (66). Post chain (engine.js:93): RenderPass, UnrealBloom (with a full-res additive blend), TiltShift (two full-res draws of 13 taps each, postfx.js:215-231), OutputPass, GradePass (3 taps). All of these use HalfFloat targets (EffectComposer.js:27). MEASURED in headless Chromium at a 1440x800 viewport, DPR 2: quality 'high', pixelRatio 1.8, renderSize 2592x1440 (3.73 MP), 5 enabled composer passes, render-target type HalfFloat (run5.log). Field census on high: 9 PointLight, 1 SpotLight, 2 DirectionalLight (one with a 2048x2048 shadow), 146 draw calls per frame (run3.log). The only remedy is the manual settings menu; no frame-time check exists anywhere.
- Suggested fix: 1) Replace the height-only cap with a pixel budget: pr = min(dpr, cap, sqrt(budget / (cssW * cssH))), with a budget of about 2.1 MP on high, 1.2 MP on medium and 0.6 MP on low. 2) Add a frame-time governor: if the median frame time exceeds 20 ms over about 2 s in the field, lower pixelRatio in steps, then quality. Apply light-count changes only during a transition so the recompile is hidden. 3) Run tilt-shift at half resolution (the blur is low-frequency; mix the sharp band from the full-res source). Fold the OutputPass tone mapping into GradePass, so there is one display-space pass and RGBA8 can be used after tone mapping.
